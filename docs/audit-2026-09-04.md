# Codebase audit — 2026-09-04

Scope: full read-only review of the Seer repository at commit `8d17fce`
(v0.6.1) covering security, correctness and concurrency, architecture and
build/CI, and test coverage. Every finding below was verified by reading the
cited code; where behaviour depends on server or OS runtime that is stated.

Baseline: `swiftlint --strict` and `swiftformat --lint` both pass with zero
violations. 219 non-generated Swift files, ~35.6k lines. 474 XCTest cases in
11 test bundles, 472 of which run in CI.

Severity key: **Critical** = data loss / feature broken for all users,
**High** = crash or silent misbehaviour on a common path, **Medium** = wrong
in a real but narrower scenario, **Low** = hygiene, performance, drift.

---

## 1. Critical

### C1. Default downloads save an HLS playlist as `.mp4` — offline playback is broken

- `Packages/DownloadClient/Sources/DownloadClient/Services/DownloadManager.swift:179`
  defaults `quality` to `.high`; no caller passes a quality
  (`Features/Library/MediaDetailView+Downloads.swift:21,120`).
- `Packages/DownloadClient/Sources/DownloadClient/Models/DownloadQuality.swift:46-55`:
  `.high` has a non-nil `maxWidth`.
- `Packages/PlaybackClient/Sources/PlaybackClient/Services/StreamURLBuilder.swift:305-316`:
  any quality with `maxWidth != nil` goes to `buildTranscodedDownloadURL`,
  which returns `/Videos/{id}/master.m3u8` (`:383-387`).
- `DownloadManager+BackgroundSession.swift:44` names the result `{itemID}.mp4`
  and marks the download `.completed`.
- The `downloadQuality` `@AppStorage` in `Features/Downloads/DownloadSettingsView.swift:9`
  is written by the picker but never read by the download path.

Result: tapping Download stores a few-hundred-byte m3u8 text file, the UI
shows "Downloaded", and offline playback fails. Every MKV is affected
regardless of quality because incompatible containers also take the
transcode branch.

Fix: for transcoded downloads use Jellyfin's progressive endpoint
(`/Videos/{id}/stream.mp4?static=false&container=mp4&videoCodec=h264&audioCodec=aac&maxWidth=…&videoBitRate=…`)
or only offer `/Items/{id}/Download`; read the user's quality setting in
`DownloadManager`.

### C2. Downloads completed while the app is not running are discarded

- `Packages/DownloadClient/Sources/DownloadClient/Services/BackgroundSessionManager.swift:238-242`:
  `didFinishDownloadingTo` resolves the download only from the in-memory
  `taskMap`; on a miss it returns without moving the file, and the system
  deletes the temp file.
- On a background relaunch `App/SeerApp/SeerAppDelegate.swift:270-279`
  creates the session manager, but its delegate and `taskMap` are populated
  only in `SeerApp.setupServices()` (`App/SeerApp/SeerApp.swift:143-191`),
  which runs from a SwiftUI `.task` and never in a UI-less launch.
- `DownloadManager.swift:147-154` then resets the record to `.pending` and
  re-downloads from scratch.

Fix: resolve `taskIdentifier → Download` from `DownloadStore`
(`Download.taskIdentifier` is already persisted, `DownloadStore.swift:143`),
always move the file to a stable location keyed by task identifier before
returning, and construct `DownloadManager` in
`application(_:didFinishLaunchingWithOptions:)`.

## 2. High

### H1. Crash: `Dictionary(uniqueKeysWithValues:)` on `CachedMediaItem.id`, and the app creates the duplicates itself

- `Packages/OfflineSync/Sources/OfflineSync/Services/MediaItemSyncService.swift:235`.
- `syncLatestItems` / `syncContinueWatching` (`:218-229`) insert items with
  `libraryId == nil`; `syncLibraryItems` (`:193`) fetches existing rows by
  `libraryId == L` (`:390-394`), misses them, and inserts a second row with
  the same `id` (`:410-411`). The next latest-items sync fetches by id, gets
  two rows, and traps.
- The CloudKit-backed store forbids unique constraints
  (`CachedMediaItem.swift:42`), so two devices syncing the same library also
  produce duplicates. Same pattern at
  `Features/Requests/RequestsViewModel.swift:180-182` for `CachedRequest`.

Scenario: watch a movie (appears in Latest), browse its library, return to
the Library tab → crash on every launch thereafter.

Fix: `Dictionary(_:uniquingKeysWith:)`, dedupe on
`(serverConfigurationID, id)` rather than `libraryId`, delete surplus rows.

### H2. `NotificationStore` mutates SwiftData objects on the wrong context — request status updates never persist, notifications repeat

- `Packages/NotificationClient/Sources/NotificationClient/Services/NotificationStore.swift:69-96`:
  `upsertCachedStatus` creates context C2 but `existing` came from
  `fetchCachedStatus`, which used its own throw-away context C1. The mutation
  is on a model whose context is gone; `C2.save()` persists nothing.
  `deleteCachedStatus` (`:100-106`) deletes an object owned by another
  context. `savePreferences` (`:32-44`) inserts an instance registered to a
  different context.
- `RequestStatusPoller.swift:79-88` therefore detects the same transition on
  every poll: an "approved" notification every 15 minutes, indefinitely.

Fix: fetch, mutate and save on one context (or make the store a
`@ModelActor`); return `Sendable` snapshots instead of `@Model` instances.

### H3. `@Model` instances escape their contexts under `@unchecked Sendable`

- `DownloadStore.swift` creates a fresh `ModelContext` per call and returns
  `Download` objects (`:15-21, :35-40`). `DownloadManager.downloads`
  (`DownloadManager.swift:15,168`) retains them for SwiftUI.
- `Download.swift:181`, `AutoDownloadRule.swift:108`,
  `CachedRequestStatus.swift:44`, `NotificationPreferences.swift:51` are
  `@unchecked Sendable` to make this compile. Reading a `@Model` after its
  context is deallocated is unsupported and masks real races.

Fix: one long-lived context per actor; hand the UI `struct DownloadSnapshot:
Sendable` DTOs.

### H4. Closing the player while media loads leaves invisible background playback and an endless progress loop

- `Features/Playback/VideoPlayerView.swift:84-91`: an uncancelled `Task`
  awaits `loadMedia` then calls `play()`. `onDisappear` (`:93-100`) runs
  `stop()` first, which is a no-op because `player` is still nil.
- `Features/Playback/VideoPlayerViewModel.swift:145-149` then creates the
  player, `play()` (`:241-252`) starts audio (background-audio mode is on),
  and `startProgressReporting` (`:495-505`) captures `self` strongly.

Fix: store and cancel the load task in `stop()`; guard `play()` on a
`stopped` flag; `[weak self]` in the progress loop.

### H5. After PiP restoration nothing ever calls `stop()`; player, controller and view model leak and keep reporting

- `Packages/PlaybackClient/Sources/PlaybackClient/Services/PiPPlaybackManager.swift:226-252`
  re-presents the same `AVPlayerViewController` via UIKit and keeps the
  coordinator in `pipDelegate` (`:161`). Closing it hits
  `willEndFullScreenPresentation` (`VideoPlayerView.swift:276-293`) →
  `dismiss()` of an already-dismissed SwiftUI view. `pipDidStop()`
  (`:167-182`) neither pauses nor releases the delegate.

Fix: on non-restoring `pipDidStop` pause + `stop()` + release; in the
UIKit-restored flow handle `playerViewControllerDidEndDismissalTransition`.

### H6. `LibraryViewModel` keeps the previous server's service after a switch

- `Features/Library/LibraryViewModel.swift:77-86`: `setupService()` runs only
  from `init`. `LibraryView.swift:54-57` reacts to `activeServerID` with
  `refresh()`, which reuses the stale service, URL and config ID. Discover,
  Search and Requests view models do rebuild correctly.

Fix: add `serverChanged()` that re-runs `setupService()`.

### H7. tvOS is advertised but cannot build and is never built

- `project.yml:42` lists tvOS; `:84` `TARGETED_DEVICE_FAMILY: "1,2"` excludes
  Apple TV; `:542-543` (own comment) says the wifi-info entitlement blocks a
  tvOS build. CI, `Makefile` and `fastlane/Fastfile` only target iPhone 17.
- ~60 unguarded iOS-only API sites (`navigationBarTitleDisplayMode` ×23,
  `presentationDetents` ×8, `keyboardType` ×6, `CaptiveNetwork`,
  `BGProcessingTask`, `UIActivityViewController`…). Only 4 `os(tvOS)` guards
  exist. `Features/Playback/TVPlayerView.swift` is unreferenced.
- tvOS is claimed in `CLAUDE.md`, `site/index.html:74,81`,
  `fastlane/metadata/en-US/description.txt` and
  `apple_tv_privacy_policy.txt`.

Fix: either drop tvOS from `supportedDestinations`, docs and store copy, or
add a `generic/platform=tvOS` CI build and gate the sites above. The App
Store copy currently makes a claim the binary cannot fulfil.

## 3. Medium — security and privacy

### S1. App Transport Security disabled globally
`App/SeerApp/Info.plist:65-69` sets `NSAllowsArbitraryLoads`. The Jellyfin
password is POSTed in `Users/AuthenticateByName`
(`JellyfinService.swift:80-92`) and Bonjour-discovered servers are always
`http://` (`BonjourDiscovery.swift:130`). Replace with
`NSAllowsLocalNetworking = true`, warn on non-local `http://`, require
`https` for the OTLP endpoint.

### S2. Jellyfin access token in URL query strings for all streams and downloads
`StreamURLBuilder.swift:221,366,395,440-462` appends `api_key=` for every
stream type including DirectPlay; `VideoPlayerViewModel.swift:374` builds
`AVPlayerItem(url:)` with no headers. The long-lived token lands in server,
proxy and CDN logs. Use the `Authorization: MediaBrowser … Token=` header
(`BackgroundSessionManager.startDownload` already accepts headers) and
`AVURLAssetHTTPHeaderFieldsKey` for AVFoundation; keep query auth as an
explicit fallback only.

### S3. Token-bearing URLs printed unconditionally
`VideoPlayerViewModel.swift:371`, `DownloadManager.swift:383`. 82 `print`
sites overall vs 19 files using `os.Logger`. Redact and move to `Logger`
with `privacy: .private`.

### S4. OTLP auth header is effectively public
Expanded into `Info.plist:113-116`, which is not encrypted in the shipped
app; `release-please.yml:112-119` also uploads the IPA as a 30-day artifact
on a public repo. Treat as an ingest-only, rate-limited, rotatable key or
front it with a proxy; drop or narrow the IPA artifact upload.

### S5. In-app privacy link points at a domain the project does not control
`Features/Feedback/PrivacySettingsView.swift:125` and
`DiagnosticsConsentSheet.swift:150` open `https://seer.app/privacy`; the
policy actually lives at `cedricziel.github.io/seer-app/privacy-policy.html`
(`fastlane/metadata/en-US/privacy_url.txt`). Point both at the real URL and
add a test asserting equality with `privacy_url.txt`.

### S6. Privacy policy understates iCloud sync
`site/privacy-policy.html:112` says URL/username/password live in the
Keychain. In fact server URLs, user ID and Wi-Fi SSIDs
(`ServerConfiguration.swift:4-21`), plus cached library items, watch
progress and requests (`SeerApp.swift:33-44`) sync to the CloudKit private
database. Update the policy; consider keeping SSIDs device-local.

### S7. Lower-severity security items
- Consent revocation does not stop exports until relaunch
  (`TelemetryService.swift:233-242, 253-284`); persisted spans are replayed.
- Download paths built from server-supplied `itemID` / `mediaType` without
  validation (`DownloadStorage.swift:49-57`). Validate `^[A-Za-z0-9-]+$`.
- Server URL entry accepts any scheme in
  `InternalURLSettingsView.swift:174` and `AddServerView.swift:97,149`;
  route through `AuthErrorFormatter.validate`.
- GitHub Actions pinned to major tags not SHAs; `ci.yml` has no
  `permissions:` block; `release-please.yml:18-20` grants `contents: write`
  to deploy jobs; `ssh-keyscan` is trust-on-first-use.
- `WiFiSSIDMonitor.swift:41-43` requests Always location; When-In-Use
  suffices unless background Wi-Fi switching is truly needed.

Checked and clean: credentials only ever touch the Keychain
(`kSecAttrSynchronizable` + `AfterFirstUnlock`, correct pairing); no TLS
bypass anywhere; no secrets in the repo or its history; telemetry and crash
reporting initialise only after consent; feedback sends nothing
automatically; deep-link router is strict.

## 5. Medium — architecture, build, CI

- **Dead code**: `Features/Playback/PlayerControlsOverlay.swift` (312 lines)
  and `AirPlayRouteButton.swift` have zero call sites; the openspec change
  `enable-airplay-playback` shipped its button into that overlay. AirPlay is
  still reachable via system controls, so this is dead code rather than a
  missing feature. Also unused: `TVPlayerView.swift`; `AppState.logout`,
  `logoutAll`, `showError`, `clearError`, `markAsUsed`,
  `loadStoredCredentials`; `JellyseerrService.getAPIKey/setAPIKey/getRequest`;
  `CookieAuthMiddleware`. Consider `periphery` in CI.
- **Docs drift steers agents wrong**: `CLAUDE.md:25` lists 2 test targets
  (scheme has 9); Xcode 16 stated where iOS 26 needs Xcode 26; module list
  omits `Features/Shared`, App Intents (14 files), `CachedRequest`,
  `SearchHistoryStore`, `RefreshScheduler`. `openspec/config.yaml`,
  `docs/fastlane.md`, `docs/releases.md`, `docs/app-store-privacy.md` cite
  files, lanes and workflows that don't exist (`beta.yml`, `bump_build`,
  `MetricsReporter.swift`, `app-store.yml`) and say data "stays on-device"
  although OTLP export shipped in 0.6.0.
- **Two disagreeing lockfiles**: `Packages/JellyseerrAPI/Package.resolved`
  pins `swift-openapi-runtime 1.11.0` but the workspace `Package.resolved`
  Xcode actually uses pins `1.9.0`; Dependabot only tracks the ignored one.
- **CI**: `macos-26` with no Xcode pin; `brew install swiftlint swiftformat`
  unpinned while the session hook pins 0.63.2 / 0.61.1; no SPM/DerivedData
  cache; lint job runs on macOS where a Linux runner would do; no Release
  build on PRs; `SeerUITestsTV` scheme never executed.
- **`SeerCore` is a kitchen sink**: 41 files importing `AppIntents`,
  `CoreSpotlight`, `CloudKit`, `CoreLocation`, `MetricKit`, `SwiftUI`, nine
  OpenTelemetry products and PLCrashReporter. Every framework transitively
  links telemetry. Split into `SeerCore` / `SeerTelemetry` / `SeerIntents`.
- **Unused OTel products** declared in `project.yml:124,130`
  (`StdoutExporter`, `URLSessionInstrumentation`);
  `OpenTelemetryProtocolExporterCommon` imported but not declared.
- **Cross-feature coupling**: Discover uses Search's cards and sheets,
  Downloads uses Library's button, four features use Servers' switcher.
  `RequestOptionsSheet` and `SharedRequestOptionsSheet` are near-duplicates.
- **Duplicated helpers**: image URL built in five places while
  `JellyfinService.getImageURL` exists; `RelativeDateTimeFormatter`
  re-created despite `Date.relativeString`; Kingfisher used directly in four
  views bypassing `PosterImage`.
- **Localization**: zero string catalogs, ~360 literal UI strings plus ~121
  user-facing strings in view models that a catalog would not extract.
- **Accessibility**: zero `dynamicTypeSize` / `@ScaledMetric`, ten fixed
  `.font(.system(size:))`, no accessibility modifiers on `MediaContextMenu`,
  `WatchProgressIndicator`, `SkeletonCard`, `SectionEmptyView`, `FlowLayout`.
- **`JellyseerrAPI` generation undocumented**: `JellyseerrAPI.swift:4`
  claims build-time generation but `Generated/` (55k lines) is committed
  with no script; upstream Jellyseerr version not recorded.
- **openspec**: `add-app-intents` (67/85) and `enable-airplay-playback`
  (17/22) shipped but not archived; four iPad proposals at 0/124 tasks.

## 8. What is in good shape

- Dependency direction (features → clients → SeerCore) holds exactly as
  declared in `project.yml`, verified by import.
- Lint and format gates clean under strict mode with one justified disable
  and zero TODOs.
- Credential handling: Keychain only, correct sync/accessibility pairing,
  per-server namespacing, deletion on server removal.
- Telemetry and crash reporting are fully consent-gated at initialisation.
- Release pipeline: prerelease graduation, reproducible build number, manual
  signing with documented rationale, secrets never tracked.
- `BackgroundSessionManager` moves files synchronously in
  `didFinishDownloadingTo`, guards state with `NSLock`, handles the
  completion handler on main.
- `SearchViewModel`, `PersonDetailViewModel`, `RefreshScheduler`,
  `QuickConnectSession` cancel tasks correctly; `PiPPlaybackManager` uses
  `[weak self]` throughout.
- Test infrastructure: every test directory is wired, snapshot diffs
  uploaded on failure, in-memory SwiftData seams exist for App Intents.

## 9. Suggested order of work

1. C1, C2 — downloads are the app's headline offline feature and are broken.
2. H1, H2 — a reproducible crash and a repeating-notification bug.
3. H4, H5, M9 — player lifecycle; all three share a `teardownPlayer()` fix.
4. H6, M1, M2, M3 — multi-server correctness; all keyed on config UUID.
5. S2, S3, S1 — token in URLs and logs, then ATS scoping.
6. H7 — decide tvOS one way or the other before the next App Store submit.
7. Test targets for NotificationClient and OfflineSync sync services.
8. Docs sweep (CLAUDE.md, openspec config, docs/*.md, privacy policy).
